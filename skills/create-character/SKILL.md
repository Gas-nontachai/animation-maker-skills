The compatible runtime is `@gasnonthachai/animation-maker@^1.1.1`, installed in the user's project. Check `node_modules/@gasnonthachai/animation-maker/package.json` and `./node_modules/.bin/animation-maker --version`. Both must report the same version satisfying SemVer `^1.1.1` (`>=1.1.1 <2.0.0`, excluding prereleases). Reuse a compatible installation without reinstalling, upgrading, querying npm or changing package.json/package-lock.json. Reject 1.1.0 and 2.0.0; accept 1.1.1, 1.1.2 and 1.2.0. On Windows use the `.cmd` shim. Never resolve a developer checkout or a global executable.

If missing or incompatible, check whether `npm view '@gasnonthachai/animation-maker@^1.1.1' version --fetch-retries=0 --fetch-timeout=10000` confirms availability. A network/permission failure is not evidence of an unpublished package; request host network approval if needed. On E404 report that no compatible runtime is available; do not pretend installation worked or substitute a local tarball. Request permission to run `npm install --save-dev '@gasnonthachai/animation-maker@^1.1.1'` when installation is needed and not already authorized. Before the approved npm install, preserve existing package.json fields and merge this scoped security mitigation into its overrides: `"@gasnonthachai/animation-maker": {"zod": "4.6.7"}`. This patches pinned vulnerable transitive Zod copies only within this runtime's subtree. Do not replace unrelated overrides; if that exact scope already has conflicting values, report the conflict for review rather than overwriting it. In a new directory create a minimal private package.json with that override. Preserve the project lockfile; let npm update it for the approved install, never delete it or force an update of an already compatible runtime. Recheck the manifest/CLI compatibility and run `npm audit` afterward; do not claim security readiness if unexpected advisories remain. The runtime's root overrides do not propagate to consumers, so this step is required even if an earlier repo audit was clean. Do not run `npx animation-maker` to implicitly fetch code; use the installed shim or `npx --no-install animation-maker`.

Choose the authoring path from the prompt:

- For the default friendly robot waving request (or an unspecified character waving), retain `./node_modules/.bin/animation-maker create --project <unused-directory>`. It generates the compatible six-part robot and three-second wave preset. Keep the right-arm shoulder pivot and downward default pose when using that preset.
- For a requested appearance or object (for example a human in a yellow shirt, coffee cup, tree, or different body shape), author the SVG source, rig and timeline directly. Do not create the default robot first and merely recolor it. Do not introduce category-specific generators, a mandatory skeleton, an external image-generation service or runtime changes.

For direct authoring:

1. Interpret the requested silhouette, colors and supported movement. Choose only the parts needed: a static cup can be one part; a human may have a torso, head, upper arm, forearm and hand with nested parents. Split independently moving geometry into separate SVG parts.
2. Reserve an unused project directory with an exclusive directory creation (no recursive creation of the project itself). If it already exists, choose another path; do not overwrite existing directories or files. Create `character/parts/` inside it and write all new source files exclusively. For explicit edits to existing assets, preserve unrelated files.
3. Generate editable SVG primitives for each part. Define attachment coordinates, pivots and parents for the requested geometry, rather than inheriting robot proportions. Each SVG needs `viewBox="0 0 width height"`. Use only static svg/g/path/rect/circle/ellipse/line/polyline/polygon and allowlisted presentation attributes. No scripts, event handlers, CSS, text, images, hrefs, declarations, entities or external resources.
4. Write `character/rig.json`: `version: "1.0"`, a unique rig `id`, positive `canvas: {width, height}`, and one or more `parts`. Each part requires a unique `id`, `asset` relative to `character/`, nullable `parent`, `position: {x,y}`, `pivot: {x,y}` and integer `zIndex`. Rotation, scale and opacity are optional. Parents must exist and be acyclic. Asset paths must stay inside the project after symlink resolution. Keep the compatible `character/` naming even for objects.
5. Write `timeline.json`: `version: "1.0"`, `characterId` equal to rig.id, integer fps 1–120, positive duration with integer duration × fps, and `tracks`. Use `tracks: []` for static assets. Default to 24 FPS and 3 seconds unless specified. For animation use only absolute local `position.x`, `position.y`, `rotation`, `scale.x`, `scale.y` and `opacity` keyframes, with finite values and strictly increasing times from 0 through duration. Easing is linear, easeIn, easeOut or easeInOut. Do not duplicate target/property tracks. Report unsupported requests such as automatic walking, sitting, typing, IK, physics, interactions, camera motion or audio; do not silently substitute a wave or promise those behaviors.
6. Run `./node_modules/.bin/animation-maker validate --project <directory>`. After the initial validation, repair generated source errors at most twice, validating after each attempt (three validations total). If still invalid, report the exact part/path or schema field, preserve sources and stop; never render invalid projects or weaken validators.

Coordinates are SVG units, positive Y down; clockwise rotation is positive. Local matrix is T(position) R(rotation) S(scale) T(-pivot). Position anchors the pivot in the parent's original SVG coordinates; parent matrices and opacity propagate. Global zIndex controls draw order. The rig canvas does not resize the 1280×720 video. Optional timeline `placement: {x,y,scale}` positions the asset; default is `{x:440,y:60,scale:1}`. Keep the requested geometry in view.

Inspect the installed runtime's `packages/animation-runtime/src/schemas/index.ts` and `scripts/project.ts` for the authoritative schema and SVG allowlists. The repository's `docs/asset-contract.md` provides complete static and multipart authoring examples (also shipped in newer runtime packages). Older compatible runtimes use the same v1.0 contracts and need no upgrade for dynamic assets.

Preserve all generated SVG, rig and timeline sources. For a complete animation/export request, follow the animate workflow through doctor, validation, render and inspect, requesting package/browser/render permissions only when needed.

## M2 scene workflow

Scene support requires an M2-capable runtime; the M1 compatibility range above alone does not establish that capability. In this unreleased checkout use its local CLI only when explicitly authorized. Do not silently install or publish an unreleased build. Read the runtime's docs/scene-contract.md before authoring scenes.

Identify independent objects from the prompt. Reuse the create-character SVG safety, part and pivot instructions for each rig; preserve Rig v1.0. Store rigs under assets/<name>/rig.json and SVGs beside each rig. Reuse rig references for repeated instances. Write scene.json and a scene timeline using explicit {object} or {object,part} targets; use tracks: [] for static scenes. Keep object layers grouped and animate only supported keyed transforms/opacity. Validate, render and inspect using the existing commands, preserving and reporting every SVG/JSON and MP4 path. Owner visual approval remains separate from automated checks. For example: “Create a 5-second animation of a yellow-shirt character raising a hand while a coffee cup moves across a desk.” Author independent character, desk, laptop and cup rigs with synchronized part rotation and cup position tracks. Do not claim walking, typing, sitting synthesis, IK, physics, interactions, camera or audio support.
