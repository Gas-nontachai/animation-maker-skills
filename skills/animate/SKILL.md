## M2 scene workflow

Scene support requires an M2-capable runtime; the M1 compatibility range above alone does not establish that capability. In this unreleased checkout use its local CLI only when explicitly authorized. Do not silently install or publish an unreleased build. Read the runtime's docs/scene-contract.md before authoring scenes.

Identify independent objects from the prompt. Reuse the create-character SVG safety, part and pivot instructions for each rig; preserve Rig v1.0. Store rigs under assets/<name>/rig.json and SVGs beside each rig. Reuse rig references for repeated instances. Write scene.json and a scene timeline using explicit {object} or {object,part} targets; use tracks: [] for static scenes. Keep object layers grouped and animate only supported keyed transforms/opacity. Validate, render and inspect using the existing commands, preserving and reporting every SVG/JSON and MP4 path. Owner visual approval remains separate from automated checks. For example: “Create a 5-second animation of a yellow-shirt character raising a hand while a coffee cup moves across a desk.” Author independent character, desk, laptop and cup rigs with synchronized part rotation and cup position tracks. For coordinated walking, sitting and interactions use the M3 capability gate below. Do not claim typing synthesis, generalized IK, physics, camera or audio support.

## M3 motion planning (capability-gated, unreleased)

For coordinated walk/sit/reach/pickup/putdown requests, first confirm the authorized runtime exposes `compileMotion` and the `plan` command and includes docs/motion-contract.md. A version satisfying the M1 range is insufficient. This implementation task authorizes its local checkout; other user projects must explicitly authorize a checkout or use an independently verified M3 release. Do not install/publish a candidate automatically. Read the motion contract before planning.

Use the existing agent for language interpretation; do not call an external LLM API. Identify independent characters/props, preserve static props, decompose requested actions and assign explicit frame-aligned starts/durations within the requested total duration. Represent stops and holds as gaps. Assign dependencies and semantic part IDs. Author prompt-specific SVG/rig assets with connected pivots and direct upperArm → forearm → hand chains with unit arm scales. Author thighs and their child lower legs for walk/sit. Check reach distances and chair placement using authored geometry; do not hardcode runtime part names or infer capabilities from appearance.

For curls, repetitions, wrist/grip or drinking requests, read [motion-quality.md](references/motion-quality.md). Distinguish endpoint-driven Reach from joint-driven motion: use existing authored rotation tracks for elbow-dominant curls and wrist tilt. Do not use Reach indiscriminately.

Preserve a strict version 1.0 motion.json and an M2 scene.json plus an initially empty valid scene timeline. Map only existing semantic parts. Use walk to approach, sit to transition, reach to contact, pickUp to attach at its end boundary, supported arm transport plus authored wrist tilt/hold to bring the prop opening to the mouth, then putDown to release. There is no drink preset, fluid simulation or arbitrary motion synthesis: disclose the supported gesture and reject requests that require unsupported capabilities. PutDown destinations refer to world contact points. Plan all object interactions explicitly; desk/chair must have no tracks unless requested.

Compile using `animation-maker plan --project <project> --output <unused candidate-timeline.json>`, then explicitly copy the successfully compiled candidate into the new project's timeline.json. Preserve motion.json and the candidate for review. A plan command requires an existing valid scene/timeline and checks the SVG/path restrictions before generation. Do not weaken validators, mutate runtime code, silently replace unsupported actions or bypass errors with hand-authored fake contact tracks. Repair source/plan errors with the existing bounded validation attempts. Stop with the exact diagnostic if capabilities or conflicts remain unresolved.

Run the existing validate → render → inspect workflow, deriving frame/metadata expectations from the plan. Decode frames at action boundaries and within attachment intervals if claiming visible motion checks. Preserve and report SVGs, rigs, scene.json, motion.json, timeline.json and MP4. Distinguish compiler validation, metadata inspection and decoded-frame evidence from owner regression/E2E/visual acceptance. See docs/m3-owner-e2e.md for the primary eight-second coffee scenario. Repeated pickup of the same object, moving ancestors during reach, sheared attachments, generalized IK, physics and automatic foot planting remain unsupported and must produce explicit diagnostics or a disclosed planning limitation.
